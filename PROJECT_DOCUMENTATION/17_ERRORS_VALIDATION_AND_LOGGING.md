# 17 — Errors, Validation & Audit Logging

## 1. Unified JSON Error Envelope

All API error responses generated by the Laravel REST API follow a predictable, typed envelope structure:

```json
{
  "success": false,
  "message": "Human-readable explanation of error.",
  "errors": {
    "field_name": [
      "The specific validation message for field_name."
    ]
  },
  "code": "ERROR_IDENTIFIER_STRING"
}
```

### Standard HTTP Status Codes

| Status Code | Meaning | Example Trigger |
|---|---|---|
| `400 Bad Request` | Malformed syntax or invalid state transition | Attempting to accept an expired quotation |
| `401 Unauthenticated` | Missing or invalid Sanctum Bearer token | Visiting `/api/v1/orders` without auth header |
| `403 Forbidden` | Valid token, but insufficient role permissions | Customer token hitting `/api/v1/admin/*` |
| `404 Not Found` | Entity does not exist | Requesting unknown product slug |
| `422 Unprocessable Entity`| Form Request validation failed | Submitting registration with duplicate email |
| `429 Too Many Requests`| Rate limit exceeded | > 5 login attempts within 60 seconds |
| `500 Server Error` | Unhandled runtime exception | Database connection timeout |

## 2. Form Request Validation Layer

Incoming payloads are validated by dedicated Form Request classes before entering controller methods.

Example: `backend/app/Http/Requests/Catalog/StoreProductRequest.php`:
```php
public function rules(): array
{
    return [
        'name' => ['required', 'string', 'max:255'],
        'sku' => ['required', 'string', 'max:100', 'unique:products,sku'],
        'wholesale_price' => ['required', 'numeric', 'min:0.01'],
        'moq' => ['required', 'integer', 'min:1'],
        'audience' => ['required', Rule::in(['MEN', 'WOMEN', 'BOYS', 'GIRLS', 'UNISEX'])],
        'design_type' => ['required', Rule::in(['ORIGINAL', 'MASTER COPY'])],
        'category_id' => ['required', 'exists:categories,id'],
        'brand_id' => ['nullable', 'exists:brands,id'],
    ];
}
```

## 3. Immutable System Activity & Audit Trail

The platform records administrative mutations in the `activities` table via `backend/app/Services/Audit/ActivityLogger.php`:

```sql
CREATE TABLE activities (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id) ON DELETE SET NULL,
    action VARCHAR(100) NOT NULL,
    subject_type VARCHAR(255) NULL,
    subject_id BIGINT NULL,
    description TEXT NULL,
    ip_address VARCHAR(45) NULL,
    user_agent TEXT NULL,
    properties JSONB NULL,
    created_at TIMESTAMP NULL
);
```

### Logged Operations:
- `product.create`, `product.update`, `product.delete`
- `inventory.adjust` (captures previous stock, new stock, reason code)
- `order.payment_verify`, `order.status_update`
- `homepage.featured_brands_sync`, `homepage.hot_sale_sync`
- `rfq.status_change`, `quotation.create`

## 4. Framework Logging Configuration

Configured in `backend/config/logging.php`:
- **Local Development**: `stack` channel routing to `storage/logs/laravel.log`.
- **Production**: `daily` rotation channel with 14-day retention or centralized syslog streaming.
- **Sensitive Data Masking**: Monolog processors scrub credit card numbers, passwords, and authorization tokens before writing log lines to disk.
